How it works

01 THE LOOP

What happens when you press Save

The document holds its own interface, behaviour, content and state. Saving serialises the live DOM into one string and does three things with it.

  1. The bytes go to a Blossom server as a blob addressed by their own sha256. Uploading is authorised by a signed kind-24242 token.
  2. A NIP-5A manifest maps /index.html to that hash. It is a replaceable event, so publishing a new one is the deploy.
  3. A kind-5128 snapshot records that set of hashes as a permanent version.

A gateway resolves the manifest, fetches the blob, checks that the bytes hash to what the manifest claims, and serves them. Nothing in that loop is a server you run.

The DOM is the database. There is no second place where state lives. Save the page, open the file in a text editor, and what you typed is right there in the markup.

02 DEPLOY

Getting a page online

The CLI publishes the first version. After that the page republishes itself, and you come back to the CLI only for changes made outside the browser.

# scaffold a document and generate a key for it
npx nsite-clay init mysite

# publish
npx nsite-clay deploy mysite --sec=nsec1…

init prints the key once and stores it nowhere. It is the only thing that can publish the site, so save it before you close the terminal. To use a key you already have, pass --npub= instead and the document is written with that owner.

Signing through a remote signer keeps the key off the machine doing the deploy, which is what you want on a shared machine or in CI:

# prefer the environment: an argument is visible in the process list
export NOSTR_BUNKER_URI="bunker://…"
npx nsite-clay deploy mysite

The connection belongs to a client key, which is saved per bunker under ~/.config/nsite-clay/bunkers.json and reused. A bunker:// secret is single use, so without that the second deploy would arrive as an app the signer has never seen.

Where it ends up

SiteURL
root site (the default)https://<npub>.nsite.lol/
named site (--site=blog)https://<base36 pubkey>blog.nsite.lol/
one specific versionhttps://v<base36 snapshot id>.nsite.lol/

Any NIP-5A gateway serves the same site, so a CNAME pointed at one gives you a custom domain. A key has one root site and as many named sites as you like.

03 LOCALLY

A whole stack on your laptop

Developing against public relays means publishing every experiment to somebody else's disk and every half-finished draft to a public gateway. None of the three services involved is complicated enough to justify that, so the repository ships all three, in memory.

npm run devnet

  relay    ws://127.0.0.1:4869
  blossom  http://127.0.0.1:4870
  gateway  http://127.0.0.1:4871

Deploy into it by pointing the two flags at localhost, then open the site at its canonical hostname. Browsers resolve anything under .localhost to the loopback address, so the npub goes in the hostname exactly as it does in production.

npx nsite-clay deploy mysite --sec=nsec1… \
  --relays=ws://127.0.0.1:4869 --servers=http://127.0.0.1:4870

open http://npub1….localhost:4871/

It keeps nothing. Stop the process and every event and blob is gone, which is the point. It is a development fixture: it trusts its caller and should never be reachable from anywhere but your own machine.

04 SIGN IN

Reading, then editing

Signing in as the owner arms the editable regions and reveals the save controls. Three ways in, ranked by how much you have to trust the page in front of you.

  • A NIP-07 extension. The key never enters the page.
  • Amber or another NIP-46 signer. The key never enters the browser. The page shows a nostrconnect:// QR and a deep link, and each signature is approved on your phone. This is the right default for a page served by a gateway you do not control.
  • A typed key. nsec1…, 64 hex characters, or a NIP-49 ncryptsec1… with its password. It lives in the tab for the session and is written nowhere. The field is a password field on purpose: the snapshot algorithm never writes those values into markup, so a save cannot bake your key into the page it publishes.

05 TEXT

Adding a paragraph, or a heading

Mark a container editable and type into it. Enter starts a new paragraph. Selecting text raises a toolbar whose first control is a block menu, which turns the current block into a heading, a list, a quote or a code block.

KeysDoes
⌘B ⌘I ⌘Ubold, italic, underline
⌘Klink, or unlink when the selection is already one
⌘⇧7 ⌘⇧8 ⌘⇧9numbered list, bulleted list, quote
⌥0 to ⌥3paragraph, then the three heading levels
# - > at the start of a block, the same thing by typing
⌘Ssave, whether or not autosave is on

Use editable="single-line" for a title or a list row, where Enter should do nothing and a block menu makes no sense.

What reaches the file is markup a person could have written. The editable attribute stays as an inert marker; the contenteditable it implies, the toolbar, and the debris browsers emit from editing commands are all stripped. Pasted markup goes through a sanitiser, so copying out of a word processor does not smuggle a stylesheet into your document.

06 MEDIA

Images and video

Both live on the toolbar and both take either a URL you already have or a file, uploaded to the same Blossom servers the document is stored on. An uploaded file is content-addressed, so its URL never has to change.

An embed is inserted as a facade rather than an iframe: a poster image and a real link to the video. The player is only loaded once a reader clicks it.

Why a facade. An iframe in the saved markup would load a third-party player, and its cookies, for every reader who never asked to watch anything. Here nothing external runs until someone clicks.

07 FEEDS

Pulling Nostr content into the page

A feed widget shows short notes, long-form articles or picture posts from any npubs you name. The vocabulary follows oracolo's blocks, which got the shape right: a type, how many, a style, and an optional minimum length.

<div nc:feed="articles" nc:authors="npub1…, npub1…"
     nc:limit="5" nc:style="grid" nc:pinned="my-first-post"></div>
AttributeMeaning
nc:feednotes (kind 1), articles (kind 30023), images (kind 20)
nc:authorsone or more npubs, comma separated
nc:limithow many to show
nc:stylelist or grid
nc:min-lengthskip anything shorter, for filtering out one-liners
nc:topiconly events carrying this t tag
nc:pinnedarticle slugs, or event ids for notes, held at the top
nc:feed-relaysrelays for this widget, if not the document's own

Pinning an article uses its slug, not its event id. Long-form posts are replaceable, so the id changes every time the author fixes a typo and an id-pin would break; the slug does not move.

Every event's signature is checked in the browser before anything is displayed, and its content is sanitised. Relays are transports, not authorities.

A feed is fetched, not stored. Its items are marked transient, so a save writes the widget's configuration into the file but never the posts it happened to be showing. A reader with JavaScript off sees an empty block, the same way any client-rendered feed behaves.

08 WRITE

Notes and articles, from inside the page

If the page can show your posts, it may as well write them. The composer lists what you have published and opens an editor for more.

The slug is the field that matters. A kind-30023 event is addressable, so publishing again under a slug you have used before is the edit: every long-form client shows the new text at the same address. The editor keeps published_at from the original so the date does not jump when you fix a sentence.

Short notes are kind 1 and are not replaceable. Once a note is out, it is out, and the composer says so before you publish one.

Posting and saving are separate acts. A note goes to relays; the page is published on its own. Conflating them would make it impossible to fix a typo in a note without republishing the whole site.

09 VERSIONS

Every save is kept

Each save files a kind-5128 snapshot naming an immutable set of hashes. Blobs deduplicate, so a history of a hundred saves costs about as much as the distinct documents in it.

await nc.versions()          // snapshots, newest first
await nc.readVersion(v)      // that version's HTML, hash-verified
await nc.restore(v)          // republish it as the current one

Reading a version fetches its blob straight from Blossom and refuses bytes that do not hash to what the snapshot claims, so no gateway is trusted for it. Restoring files another version, so nothing is ever destroyed. Each version also has its own permanent URL, which does mean your history is public.

10 FRESHNESS

Nobody should need a hard refresh

A published document hardcodes its asset URLs, and gateways serve them with a cache lifetime. Replacing a file at the same path is therefore invisible to a browser that already has one. Two mechanisms deal with it, and they only work together.

  • Assets are published at paths carrying their content hash, so a new build is a new URL that no cache can satisfy from stock. The unfingerprinted path stays in the manifest as an alias to the same blob, so a reader holding the previous document does not break.
  • Each document watches its own manifest. That manifest is a replaceable event, so a new version arrives as a push rather than a poll: when the hash for the document's path stops matching the bytes the tab was served, the page says so and reloads itself through a cache-proof URL.

A page with unsaved work is never reloaded out from under you, and the watch only runs on the document's canonical address. A local copy is a different artifact, not a stale one.

11 LIMITS

What it will not do

  • One key writes the document. The manifest carries one signature. No shared editing, no per-visitor content.
  • No conflict detection. A replaceable event has no compare-and-swap, so two devices editing at once will silently lose one side's work.
  • The gateway is trusted for the first byte. Everything the document loads afterwards is hash-checked and every event is signature-checked, but the entry document cannot verify itself. The manifest, the blobs and the history all live outside the gateway, so you can check the same document through another one or run your own.
  • No server code. If the project needs a backend, this is the wrong tool.
