# AI workflow audit: 0.3.0 through 0.3.14

Method: dual-agent review (A: `ses_f2f606d98ffevUGzAonSfEdZnO`, B: `ses_f2a82b679ffeNG4ERT6ZBIjo7k`), supplemented by source review and regression tests.

## Verdict

The product has a coherent idea: describe a page, inspect it, keep it, publish it,
then edit the page itself. The implementation still made the owner infer too
much between those steps. The main weaknesses were continuity and recovery,
particularly after paying or receiving a useful AI result. A visual redesign
would not address those problems.

The initial browser review covered desktop at 1440 x 1000 and mobile at
390 x 844. It used disposable keys and fixture AI/payment responses. BrowserOS
neo became unreachable before the second independent browser assessment and
post-change visual confirmation. Automated browser tests verified the changed
flows. No real inference or Lightning payment was made, so this audit does not
establish live model quality or production mint compatibility.

### What already works

- Ownership by key is explained before publishing.
- Preview acceptance is separate from publishing, and undo restores accepted edits.
- Refinement normally keeps the current preview when a request fails.
- Shared runtime controls let improvements reach existing pages through upgrades.

### Cognitive load and the user's experience

A first-time publisher has to learn ownership, payment and publication in one
visit. The key explanation gives that journey a sound start. Payment is the
main confidence low point; the generated preview is the reward. Losing that
preview on retry damages confidence precisely when experimentation should feel
safe.

The runtime AI settings form presents more than ten actions alongside provider
and payment fields. The 12-template list is another large decision set, although
the recommendation to start with the block composer helps. On mobile, setup and
the free route were below the first viewport. After generation on desktop, the
old Generate action remained prominent while Use this page was below the fold.

First-timers need a visible free route and payment prerequisites. Returning
payers need a resume action. Frequent users need retained instructions and
efficient refinement. Keyboard users need a genuine modal boundary.

## Findings fixed in this working tree

| Priority | Finding | Change |
| --- | --- | --- |
| P1 | Check payment had an empty handler. Delivery failure set the payment as finished before it succeeded. | Manual checking now works, errors offer a retry, and overlapping checks are prevented. |
| P1 | A seed and counter did not identify the interrupted mint request. Closing the page could strand setup. | Save invoice details before showing it; save the quote, output range, keyset and amounts before minting; restore the exact outputs after a lost reply. |
| P1 | Failed replacements discarded a paid preview. | Keep the last successful result until its replacement succeeds, including when editing the description. |
| P1 | Whole-page acceptance lacked the element editor's owner and stale-result checks. | Check ownership at acceptance and reject a result if the page has changed. |
| P1 | The static builder could remove live feeds, forms or custom scripts during a whole-page rewrite. | Refuse that route before inference and explain selected-text editing. Supporting full rewrites of these pages requires a different preservation contract. |
| P2 | Review and continuation were below the fold after generation. | Focus the review heading, scroll to the result, put Use this page before the frame and demote fresh generation. |
| P2 | Runtime preview rejection lost the instruction. | Retain instruction and scope in this editing session; add Back to my instruction and a Save/Undo reminder after acceptance. |
| P2 | Payment prerequisites were revealed too late. | Show the 2000-sat split and funded-wallet requirement before setup, with an early free-template link. |
| P2 | Dialog focus could escape onto editable background content. | Use native modal dialogs, label them, announce status, restore focus and reject duplicate submissions. |
| P2 | Settings restored stale disabled states after a key arrived. | Recompute key-dependent actions when an operation finishes. |
| P2 | A preserved photo could also be reassigned to an empty frame. | Count images with retained sources as already matched. |
| P2 | A rewrite's HTML/body styling hooks did not follow its CSS into the live page. | Carry class, direction and inline styles as part of the undoable replacement. |
| P2 | Whole-page prompts included owner metadata and editor markup. | Remove ownership metadata, scripts and editor controls from model input. |
| P2 | Local integration tests could attach to a developer's existing devnet and leave orphan processes. | Allocate isolated ports and terminate the publisher and its child gracefully. |

## Highest-value next work

1. **Separate buying credit from configuring AI.** Add AI credit should open an
   amount and payment method, with current balance and the next action. Provider,
   URL and model belong under Advanced. Backups and withdrawals are separate
   tasks. The current dialog still requires users to understand the system's
   internals to buy a small amount of credit.
2. **Restore the complete provider setup.** The relay vault currently saves keys
   by endpoint, not the provider mode and model. A custom-provider key arriving
   on a fresh browser can inherit the default model or URL-normalisation rules.
   Save and restore endpoint, mode and model together. Expose failed relay backup
   rather than silently letting users assume credit will follow them.
3. **Make AI capabilities and cost concrete.** Key presence is not balance.
   Display a verified balance when available and distinguish unavailable,
   checking, insufficient and ready states. Estimate costs from current provider
   rates instead of promising a fixed number of pages. Explain that generation
   creates static pages and photo spaces; it does not upload photos or implement
   a backend.
4. **Support iteration on the proposed runtime page.** The publisher can refine
   a preview, but the runtime currently goes back to the original page and
   instruction. A proposed-page revision history and an explicit current/proposed
   switch would make repeated changes easier to judge. Persist drafts locally
   or offer a download so a reload does not lose a paid draft; this pass only adds
   an unload warning in the publisher.
5. **Preserve live features structurally before enabling their whole-page AI
   rewrites.** Keep feeds, scripted widgets, forms, block libraries and their
   identifiers outside the model's replaceable region, or accept constrained
   patches. Sanitisation is necessary but is not a functional-preservation test.
6. **Test real-model quality separately from plumbing.** Maintain a small corpus:
   multilingual cafe page, event, portfolio, photo-heavy rewrite, mobile layout,
   long page and live-feed page. Check editability, preserved facts and assets,
   working links, visible next action and narrow-screen rendering. Record model,
   latency and cost. Fixture replies test mechanics, not model quality.

## Further reliability follow-ups

- Define concurrent-device behaviour for vault writes and wallet counter
  reservation. The current relay record is replaceable, not a transaction lock.
- Test ambiguous payment outcomes against the real node and mint, especially
  credit redemption or withdrawal succeeding while its HTTP response is lost.
  Refund recovery and the wallet's general-purpose swap path need their own
  durable transaction records.
- Replace positional photo recovery with stable asset identifiers where
  possible. Position alone cannot establish which photo belongs in a redesigned
  section.
- Continue translating actionable errors from the underlying client and wallet;
  some still surface in English on translated pages.
- Shorten release notes for the owner-facing upgrade dialog. A short outcome and
  consequence usually serves the owner better than a long account of the bug.
- Repair remaining documentation assumptions as the flow evolves. This pass
  corrects README and agent-brief claims about template-based generation and
  element-only editing.

## Verification and scan interpretation

Final checks passed: `npm run site:build`, `npm test` and `git diff --check`.
The suite includes 331 runtime checks, 24 local end-to-end checks, all four
publisher languages, AI client, clipboard, vault, Cashu and wallet tests.

Regression coverage now includes failed-generation preview retention, payment
resume after reloading, no second invoice or mint during credit retry, refused
recovery writes, lost mint replies, reordered restoration outputs, stale
whole-page proposals, owner checks, retained instructions and page styling hooks.
The end-to-end fixture publishes an AI page to a local relay/storage stack,
opens its separate origin, restores credit, rewrites the page, saves it and
checks the visitor's served copy.

The independent detector reported seven findings on the publisher: five contrast
records, one uppercase-label record and one placeholder-stripe advisory. Source
inspection suggests overridden shared tokens and inferred white backgrounds
explain the contrast records; they are not verified rendered defects. The
uppercase label and missing-image stripes were classified too broadly. A scan
of changed runtime UI also flags the existing notice accent border. No palette
redesign was justified by this evidence, and no browser overlay was available.

Questions skipped: the request already authorised focused improvements. The
next recommended design task is the dedicated credit-purchase flow above.
